## What This Project Is

**Business.Translations** (`BusinessTranslations` on NuGet) is a .NET package that adds a **translations management dashboard** to any ASP.NET Core app: a dashboard UI at `/{basePath}/dashboard` (default `/bt/dashboard`), a CRUD REST API for translations/modules/languages, and automatic table creation (`BTLanguages`, `BTModules`, `BTTranslations`) â€” the dashboard triggers `POST /bt/createTables` on first load (idempotent). All request DTOs are validated with FluentValidation; authorization is optional via `config.UseAuthorizationFilter(myFilter)`.

```csharp
app.UseBusinessTranslations(config =>
{
    config.UseSqlServer("your-connection-string");
    // config.BasePath = "bt"; // optional
});
```

### Backend layout (`Business.Translations.API`)

- `core/configuration/` â€” `BTConfiguration` (builder pattern), `DatabaseProvider` enum
- `core/extensions/` â€” `UseBusinessTranslations()` entry point (throws if no provider configured)
- `features/translations/data/` â€” datasources (raw SQL via `Microsoft.Data.SqlClient`), models, `DatabaseSeeder`
- `features/translations/presentation/` â€” `BusinessTranslationEndpointBuilder.cs` (all endpoint registrations), `entities/` (DTOs), `validators/`, `services/` (`ValidationService` static dispatch)

The API csproj has a `ProjectReference` to the FrontEnd csproj; its `BuildDashboard` target runs `pnpm run build` (in the FrontEnd folder) and **embeds `dist/**` as resources in the API assembly** — this is how the NuGet package ships the dashboard. Serving uses `EmbeddedFileProvider` (a physical `dist/` folder containing `index.html` next to the app binary wins as a dev override). The ProjectReference is `PrivateAssets="All"` so the FrontEnd never becomes a NuGet dependency. **Building the API requires pnpm/node.**

## Git, Artifacts & Style

- **Git:** recent history uses conventional-commit style (`feat:`, `fix:`, `docs:`, `chore:`) with a concise summary; keep that when committing (commits themselves stay user-driven â€” see Workflow Rules). Default branch: `main`.
- **Never hand-edit generated artifacts:** `Business.Translations.FrontEnd/dist/` (regenerated by `pnpm run build`, embedded into the package) or any `bin/`/`obj/`. Fix the source and rebuild.
- **Dependency direction (currently holds, keep it):** backend `core/` never references `features/`; frontend `core/` never imports from `src/`. The reverse is expected.
- **C# style:** file-scoped namespaces; `var` + target-typed `new()`; collection expressions (`[]`); guard clauses via `ArgumentNullException.ThrowIfNull`/`ThrowIfNullOrWhiteSpace`. SQL is always parameterized (`AddWithValue`) â€” never string-interpolate user input.
- **Tests:** test the real implementation; don't duplicate logic in tests. Data access is tested against a real SQL Server (Testcontainers), mocks are limited to unit-test boundaries (NSubstitute) and the E2E API route mocks.

## Workflow Rules (user-mandated)

- **Never commit.** Make changes, stop, let the user review. No `git commit` / `git push` unless explicitly asked.
- **Never touch anything outside the project folder — NEVER, EVER.** All work stays strictly inside the repository folder (the directory containing `AGENTS.md`). Do not write, edit, delete, install, or configure anything anywhere else on the machine or network — home directory, global caches, machine config, environment, tools, services, registry, any other drive or system location. If a task seems to require changing something outside the project folder, STOP and explain what is needed so the user can do it themselves.
- **Never touch unrelated code.** Only modify code required by the task you are currently implementing. Do not refactor, clean up, reformat, or "improve" any code that has nothing to do with the current task.
- **Never commit secrets.** No API keys, tokens, or non-local-dev connection strings in code, config, logs, or commit messages. Local-dev-only values (Docker SQL `sa` password, `Business.Translations.SampleApp/appsettings.json`) are the accepted exception; real secrets go through user-secrets/env vars. Check diffs for credentials before staging.
- **Test-first, always.** Write the failing test BEFORE implementation (bug fixes include a regression test reproducing the bug). Suite placement:
  - Backend validation/config â†’ `Business.Translations.UnitTests`
  - Backend endpoints/data access â†’ `Business.Translations.IntegrationTests`
  - Frontend UI behavior â†’ `Business.Translations.E2E` (mock API routes like `dashboard.spec.ts` does)
- **Testing philosophy (behavior over implementation).** Favor integration/E2E tests over unit tests — a test must survive a refactor. Tests assert observable behavior of the real system (endpoints, data access, rendered UI), never implementation details. Never test mock behavior in place of app behavior; mocks are only acceptable at test boundaries (see "Tests" under "Git, Artifacts & Style"). Agents will write whatever tests you allow — these opinions are the guardrail.
- **Review before done.** After completing a feature (not one-line fixes), run a code-review pass — dispatch a fresh code-review subagent to check the actual diff against the task requirements (via the `requesting-code-review` skill) — and address or explicitly flag every finding before reporting completion.
- **Skills ship with the repo.** All agent skills (team skills + vendored [superpowers](https://github.com/obra/superpowers) workflow skills) live in `.opencode/skills/` and are auto-discovered by opencode for anyone who clones the project — see `.opencode/skills/README.md`. Update them by copying newer `SKILL.md` folders in and committing.
- **Feature-based architecture everywhere.** Shared/cross-cutting code â†’ `core/`; feature code â†’ `features/` (backend) or feature folder under `src/` (frontend). No loose one-off files at project roots. Mimic neighboring files before inventing anything.

### Backend conventions

- Vertical-slice layout (`core/` + `features/translations/`).
- Every new request DTO gets a FluentValidation validator wired into `ValidationService`.
- Data access stays in datasource classes; endpoints stay thin: validate â†’ datasource â†’ response.
- Extend `BTConfiguration`'s builder pattern for new providers (e.g. future `UseMongoDb()`), not ad-hoc config fields.

### Frontend conventions

- Layout: `core/` (shared: errors, sql â€” included in tsconfig alongside `src/`) + `src/translations/` split into `data/`, `domain/types/`, `presentation/` (`components/`, `hooks/`, `pages/`, `stateManagement/`, `constants/`).
- **Data flow:** component â†’ custom hook / Zustand store (`translation-store.ts`) â†’ datasource (`fetchApi` wrapper) â†’ API. Components stay small and presentational; fetching/mutation logic lives in store or hooks, never in components.
- Use custom hooks for side effects (see `use-dark-mode.ts`); export via `hooks/index.ts` barrel. Split growing components â€” modals go under `components/modals/`; export shared pieces via `components/index.ts`.
- **Dark/light mode is mandatory:** class-based (`.dark` on `<html>`/`<body>`, toggled by `useDarkMode`, persisted in localStorage). Every new UI surface needs Tailwind `dark:` variants â€” backgrounds, text, borders, inputs, hover. Never hardcode light-only colors.
- Reuse theme tokens from `index.css` (`--color-primary: #137fec`, `.bg-primary`, `.text-primary`, `.border-primary`) instead of raw hex.
- Naming: files/folders **kebab-case** (`translation-row.tsx`); hook files prefixed `use-` (`use-dark-mode.ts`); components **PascalCase named exports** matching the file (`SettingsPage` in `settings-page.tsx`); hooks camelCase (`useDarkMode`); types PascalCase â€” plain names for UI types (`Translation`, `Module`, `UiLanguage`), `*Request`/`*Response` suffix for DTOs, `Bt` prefix for raw DB models (`BtTranslationModel`).
- Known violation: `use-Initialize-data.ts` (capital `I`) â€” don't replicate; safe to rename (one import in `translation-dashboard.tsx`).
- TS is strict (`verbatimModuleSyntax`, `noUnusedLocals`); run `pnpm run lint` and the build before handing off frontend changes.
- **Always use pnpm (never npm) for all Node work** (FrontEnd and E2E). The package manager is pinned via `packageManager` in each `package.json`; pnpm-specific settings (e.g. `allowBuilds` for esbuild's install script) live in `Business.Translations.FrontEnd/pnpm-workspace.yaml`. Lockfiles are `pnpm-lock.yaml` — don't reintroduce `package-lock.json`.

# E2E â€” mocks all API routes; needs Vite dev server on :5173

# Frontend lint / dev server (Vite, http://localhost:5173/bt/dashboard/)

**Dev-server gotcha:** the Vite dev server has **no API proxy** â€” datasources call relative `/bt/*` URLs, so against `:5173` they only work if mocked (E2E does this) or left failing. To exercise the real backend, build the FrontEnd and open the dashboard via `Business.Translations.SampleApp` (`http://localhost:5100/bt/dashboard`), which serves `dist/` and owns the `/bt/*` routes.

## Gotchas (verified this machine)

1. Missing `ConnectionStrings:TranslationsDb` â†’ code falls back to `localhost\SQLEXPRESS`, which doesn't exist here (SQL error 26). `Business.Translations.SampleApp/appsettings.json` has the Docker connection string.
2. The SQL Server container reports `unhealthy` even when fine â€” its healthcheck calls `/opt/mssql-tools2/bin/sqlcmd`, absent from `mssql/server:2022-latest`. Check logs/connect directly instead.
3. Tables aren't created at startup: call `POST /bt/createTables` once (the dashboard does it). Without it, endpoints return SQL error 208. In DEBUG builds, createTables also seeds sample data (`#if DEBUG` in `TranslationDataSource.CreateTablesAsync`); the published Release package creates tables empty.
4. Kill stale `Business.Translations.SampleApp` instances before restarting or the port is busy ("address already in use").
5. `Business.Translations.SampleApp`'s `AuthorizationEndpointFilter` passes everything through â€” no auth needed in dev.

## API Endpoints (all under /{basePath}, default /bt)

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/bt/dashboard` | React SPA |
| POST | `/bt/createTables` | Creates tables, idempotent |

| DELETE | `/bt/translations` | Bulk delete, body `{ ids: number[] }` |
| PUT/DELETE | `/bt/translations/{id}` | |
| GET/POST | `/bt/modules` | |
| PUT/DELETE | `/bt/modules/{id}` | |
| GET/POST | `/bt/languages` | |
| PUT/DELETE | `/bt/languages/{id}` | |

Validation â†’ 400, not found â†’ 404, server errors â†’ 500. Responses use an `ApiResponse` shape (`success`, `message`, optionally `data`/`error`).
